# Decision log

One entry per decision. Newest at the bottom. Add an entry whenever a choice is made that a future reader would otherwise have to guess.

| # | Decision | Reason |
|---|---|---|
| 1 | Build our own model instead of calling the Jev API | The goal is learning the training side, in particular RLCD, and an interview-ready story; an API demo would not deliver either. |
| 2 | Post-training with LoRA on a pretrained base, not pretraining from scratch | A from-scratch model on a T4 budget cannot learn enough language to read option descriptions. |
| 3 | Main backbone Qwen3-1.7B-Base; Qwen3-0.6B-Base for pipeline debugging and RLCD sweeps; 4B only as an optional QLoRA experiment | 1.7B reads option descriptions far better than 0.6B while staying clearly smaller than the 4B generator in the target agent; 1.7B still fits fp32 on a T4 if fp16 overflows, 4B does not; 0.6B makes multi-seed ablations cheap; two sizes give a scaling row in the report for free. |
| 4 | Readout via language-model logits at answer slots restricted to option letters, no custom head | Zero new parameters, one forward pass, multi-question in one sequence, and the frozen base is an immediate baseline. Per-candidate sequences (NanoJev style) are too slow to serve; a marker head is kept as a fallback if letter bias or the 26-option cap bites. |
| 5 | Options are always written into the prompt and may vary per request | This is what separates a System One model from a fine-tuned classifier; it is also what makes the unseen-intent and unseen-schema tests meaningful. |
| 6 | v1 data from public datasets (CLINC150, SST-5); LLM API used only to write option descriptions and later to synthesise rare branches; LLM also serves as a baseline | Real human text and trusted labels for a credible test set; synthetic-only evaluation would be circular. |
| 7 | Hold out 20 intents and three whole datasets that never appear in training | Evidence that the model reads options rather than memorising labels. |
| 8 | Confidence for choice and score is 1 - H(p)/ln(K) | TypeSafe has not published its formula; normalised entropy is simple, bounded in [0, 1], and recoverable from the full distribution we already return. |
| 9 | RLCD is defined operationally as policy gradient under bandit feedback with a proper scoring rule as reward, group-mean baseline and a KL term to the SFT policy | TypeSafe has published the objective but not the method; this is the reconstruction used by the public replications (Laya, eve-rlcd) and it maps onto the author's GRPO experience. |
| 10 | RLCD must be compared against SFT plus temperature scaling, and the primary claim is calibration on unseen schemas | With full labels, cross-entropy already optimises a proper score, so in-domain gains are not expected; the honest test is transfer of calibration and behaviour under partial feedback. |
| 11 | Integration host is the delta-filing agent (SEC filings, 12 MCP tools, review loop), not the insurance ReAct agent | delta-filing has many decision points of different kinds per query, so the cascade story is measurable; the insurance loop is nearly deterministic and would be better served by hardcoding. |
| 12 | The engine is built standalone first (phases 1 and 2) and integrated later (phase 3) | The interface is the contract; integration is one wrapper class once the engine exists. |
| 13 | v1 caps choice at 26 options | One letter per option keeps the readout trivial; larger sets are a v2.4 concern via a marker head or two-stage selection. |
| 14 | Project name jevmark; package jevmark; public function stays systemone | A quick search found no existing project with the name. The mark part is read as a measured reproduction: the differentiator of this project is honest evaluation (unseen schemas, RLCD ablations against temperature scaling), so the name fits the product. |
| 15 | fp16 autocast with automatic fp32 fallback on NaN or inf | T4 has no bf16; Qwen models are trained in bf16 and can overflow in fp16. The check is cheap and removes a whole class of silent failures. |
| 16 | LLM API is a mini-tier OpenAI model (GPT-4o-mini or its current successor) for descriptions and the cost baseline; the current flagship on a 200-example subset as the accuracy ceiling | Expected spend is under a dollar for descriptions and a few dollars for baselines; the caps in TASKS.md are guardrails against runaway loops, not budgets. |
| 17 | Encoding tokenizes per segment (state block, then separator plus question block for each question) and concatenates ids | Qwen's pre-tokenizer can merge `:` with following newlines when the whole text is tokenized at once, which would move the answer slot. Per-segment tokenization pins `Answer:` to a token boundary; training and inference share the one function. Raised by Claude Code during the doc review. |
| 18 | Noul has no confidence field in the response; for metrics only, noul confidence is max(p, 1 - p) | Keeps the Jev response contract while giving the coverage curve a defined rule for every question type. ECE uses top-1 probability, coverage uses the confidence field; both are stated in every report. |
| 19 | Option order in every stored split is a seeded random order fixed at build time; the API preserves caller order | Without this, gold letters cluster in test splits and letter bias becomes unmeasurable. |
| 20 | Repo hygiene: `/data/` and adapters ignored, metrics and configs committed; uv with Python 3.11; commits on main per task; tokenizer fetched from the Hub at a pinned revision, not vendored | Reports must link to committed metrics; a bare `data/` pattern would hide `jevmark/data/`; solo project needs no branches. |
| 21 | Build backend hatchling; on Linux, uv pulls torch from the PyTorch CPU index; macOS uses PyPI wheels, which are already CPU builds | Local development is CPU only and a Linux sync should never download CUDA wheels; Kaggle keeps its preinstalled torch. |
| 22 | Tiny test model: Qwen3Config with 2 layers, hidden 64, 4 heads (2 KV), head_dim 16, tied embeddings, vocab len(tokenizer); tokenizer from Qwen/Qwen3-0.6B-Base at revision da87bfb6 | The two backbones share one tokenizer; tied embeddings keep the 151k-row vocabulary to one matrix so tests stay fast on CPU. |
| 23 | On Kaggle, keep the preinstalled torch but pip install transformers, peft and datasets at the exact versions in uv.lock; applies from task 1.6 | The two environments then differ only in torch, so a local test result carries over to Kaggle. |
| 24 | Schema validation beyond the literal spec: unknown question fields are rejected; at least one question is required; instructions and option labels must be non-empty after stripping; duplicate choice labels are compared after stripping whitespace; invalid question ids are reported under the path `questions`; a JSON state must be strictly JSON-serialisable (no NaN) and its 8000-character limit applies to the rendered text | A typo such as `criterion` would otherwise be ignored silently; a JSON object cannot repeat a key, so whitespace variants are the only way two option lines can collide after parsing; the limit guards what the model reads, which is the rendered text. `serve.py` (task 1.4) must parse request bodies with a duplicate-key check, because `json.loads` keeps only the last duplicate. |
| 25 | Instructions, choice labels, choice descriptions, score level texts and noul descriptions must be single lines with no leading or trailing whitespace; the state may contain newlines | The encoding puts each of these on its own line, so a line break would forge an extra option or question line and edge whitespace would render as an invisible difference. Supersedes the whitespace-stripped duplicate comparison in decision 24: labels with edge whitespace are now rejected, so duplicates are compared exactly. Noul descriptions were added to the human's list of fields because they are rendered on option lines in the same way. Empty-string descriptions are rejected too: a description is null where null is allowed, or a non-empty string, so no option line ends in a dangling `: `. |
| 26 | Encoding details: the reference tokenizer is pinned once in `configs/base.yaml` (`tokenizer_reference`) and read by both `encode.load_tokenizer` and the tests; tokenizer assumption failures (letter tokens, parity, slot not ending in `:`) raise `TokenizerError`, a `RuntimeError`, while an over-long request raises `ValueError("max_tokens: ...")`; `encode` recomputes the 26 letter ids on every call instead of caching them | One pin avoids the test tokenizer and the parity reference drifting apart; a broken tokenizer is a setup fault, not bad input, so it must not be caught as a validation error; the encoded length belongs to no single question, so its path is the argument name; no cache means no global mutable state, at a cost of 26 short tokenizer calls per request. |
| 27 | Accept that per-segment encoding shows the frozen base (B0) an unfamiliar sequence, and state it in the v1 report | Per-segment encoding makes `:` and `\n\n` two tokens where natural text usually has the single token `:\n\n`, so B0 sees a slightly unfamiliar sequence at every slot but the last. This is a known small handicap for B0 and irrelevant after LoRA. |
| 28 | `JevMark.load` keeps all weights in fp32 and runs fp16 autocast only on CUDA when `precision.autocast` is `fp16`; `use_fp32()` switches autocast off and is the hook the first-batch NaN or inf check in the scripts (tasks 1.6, 1.7) calls; a missing `calibration.json` means temperature 1.0 and a missing `model_id.txt` means `jevmark-<run_name>`, but a checkpoint without `adapter/` is a `RuntimeError`; `load` sets eval mode and otherwise train or eval mode is the caller's choice | fp32 weights fit 0.6B and 1.7B on a T4 and make the fallback a flag flip instead of a reload; the spec gives defaults for calibration but an adapter-less checkpoint is a broken run; training switches modes around validation, so the model must not switch them silently. |
| 29 | systemone details: the default model is an `lru_cache(maxsize=1)` on `default_model()`, the one process-wide cache in the package; with `JEVMARK_CHECKPOINT` set, the run's own `config.yaml` is preferred over `configs/base.yaml`; answers are computed in float64 after renormalising the distribution, and a rounded `-0.0` is written as `0.0`; `systemone_batch` takes `batch_size` (default 16) and validates and encodes every request before any forward pass; `serve.py` reports body errors (invalid JSON, duplicate key) under the path `request`; the dev extras include `httpx` for `fastapi.testclient` | "Load once per process" needs a cache, and one explicit cached function is easier to reset in tests than a module global; a run's adapter must meet the backbone it was trained on, which base.yaml may not name; float64 keeps argmax, expectation and entropy free of fp32 noise; batching without a cap would put an arbitrarily long list into one forward pass; body errors belong to no question, and `request` is already the path for a request that is not an object. |
| 30 | Batching contract: batching has no semantic effect, and numerical differences between batched and single calls are bounded by the arithmetic precision of the run and measured in evaluation; the CPU test compares every float within 1e-4 | Batched and single forward passes are not bitwise equal (letter logits differed by about 1.5e-8 on CPU in task 1.4, and fp16 autocast on GPU will differ far more), so exact equality of 4-decimal responses cannot be guaranteed; a measured bound in metrics.json is an honest claim. |
| 31 | Dataset ids and description generation: `clinc_oos` is loaded as `clinc/clinc_oos` and `PolyAI/banking77` as its parquet mirror `legacy-datasets/banking77`, both pinned by commit in `jevmark/data/sources.py`, the one place loaders read ids from; descriptions are generated with one API call per label whose prompt lists every label of the dataset for contrast, and the spend cap is computed from reported token usage and prices given on the command line | datasets 5 needs namespaced ids and no longer runs loading scripts; the Banking77 mirror is identical row by row to the original PolyAI CSVs (docs/DATA.md section 3), so the data is unchanged; listing all labels lets each description separate its label from near neighbours; prices change, so the script cannot know them and a cap without real prices would be a fake guardrail. |
| 32 | CLINC noul balance: every out-of-scope utterance yields two records, one `out_of_scope` (true) and one `about_domain` (false); an in-scope utterance gets `out_of_scope` (false) with p = out-of-scope count / in-scope count for its split, else `about_domain`, whose asked domain is the gold one with q = N_in / (2 (N_in - N_oos)) so the extra out-of-scope `false` answers are cancelled; `build_data.py` fails if any noul kind in any split has a yes or no share outside 40 to 60 percent | The earlier rule gave about 125 true against 1200 false for `out_of_scope` in train, because train has only 250 out-of-scope utterances; a noul trained on that would learn the base rate, not the question. With q fixed at 0.5, `about_domain` in `test_indomain` would be 37 percent yes (1000 out-of-scope `false` records against about 2900 in-scope ones), so q is derived per split. The fail check makes a future imbalance impossible to miss. |
| 33 | Generated descriptions are committed as raw output and never edited; corrections go in `overrides.json` with a reason per label, and one loader applies overrides and then a fixed normalisation (curly apostrophe to straight, one trailing period stripped) to every text | The raw files stay a faithful record of what the model produced, every human correction is visible with its reason, and a single loader means no builder can read uncorrected or unnormalised text by accident. |
| 34 | Data build details: one generator per split from `random.Random(f"{seed}:{split}")`; option order uniformity is checked conditional on K (no position more than 4 binomial standard deviations from 1/K, K groups under 100 skipped) instead of on the unconditional letter histogram; `train` and `valid` files hold CLINC records followed by SST-5 records, left for the loader to shuffle; `other` has a fixed description (`None of the listed intents` for CLINC, `None of the listed options` for Banking77); SST-5 levels are checked against the dataset's `label_text` so a relabelled revision fails | String seeds make each split independent of the others; the unconditional histogram cannot be uniform when K varies and noul questions have two options, so it would be a false check; a fixed `other` text keeps that option identical everywhere; checking `label_text` guards the one place where the dataset's integer labels are trusted. |
| 35 | Evaluation details: metrics come from unrounded `forward_distributions`; macro-F1 averages over labels that occur as gold (other predictions still count as false positives); coverage is reported per question type only, since its confidence differs by type; noul symmetry reports `argmax_consistent`, the share of pairs where the answer to q is yes exactly when the answer to not q is no; a `--limit` run writes to `runs/<run_name>_limit<N>/` (gitignored); every `metrics.json` records the commit, a dirty flag and the sha256 of each data file read; `requirements-kaggle.txt` pins transformers, peft, datasets, accelerate, tokenizers and peft's direct dependencies from `uv export --frozen`, never torch; the Kaggle notebook passes the GitHub token to git through environment variables only; the Makefile takes `PY` (uv locally, python on Kaggle) and `make eval` passes `--config` only when `EVAL_CONFIG` is set | Rounded responses would hide calibration; labels never gold would dilute macro-F1 with undefined classes; pooling two confidence definitions in one curve would be meaningless; "agree" in the plain sense would count contradictions as agreement; smoke runs must never overwrite results and every number must trace to code and data; tokenizers decides the ids, so it is pinned with the rest; a token on a command line or in `.git/config` can leak into logs or outputs; the old `make eval` would have overridden a run's own config with base.yaml. |
